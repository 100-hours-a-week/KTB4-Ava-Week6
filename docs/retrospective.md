# 1. 회고

## 들어가며

이번 프로젝트에서 가장 집중하고 싶었던 영역은 백엔드였습니다.

Spring Boot와 JPA를 이용해 기능을 만드는 것 자체도 처음에는 익숙하지 않았지만, 프로젝트가 진행될수록 단순한 CRUD보다 **의존성을 어떤 기준으로 분리할지, 데이터를 어떤 구조로 관리할지, 여러 요청이 동시에 들어왔을 때 무엇을 기준으로 정합성을 보장할지**가 훨씬 어렵게 느껴졌습니다.

처음에는 기능이 정상적으로 동작하는지가 가장 중요했습니다. 하지만 마지막에는 같은 기능이라도 왜 이 구조를 사용했고, 어떤 실패 상황까지 보장할 수 있는지를 설명하는 것이 더 중요하다고 생각하게 됐습니다.

---

## 도메인을 나누는 기준을 고민하게 됐다

마지막 주차에는 댓글을 통해 선착순으로 참여하는 모임 게시글 기능을 추가했습니다.

가장 먼저 고민한 것은 정원, 마감일, 신청 인원 같은 모임 전용 데이터를 어디에 둘 것인가였습니다.

가장 간단한 방법은 기존 `Post` 엔티티에 모두 추가하는 것이었습니다. 하지만 일반 게시글에서는 이 필드들이 전부 필요하지 않고, 앞으로 참여 신청과 정원 관리 로직이 늘어날수록 `Post`가 맡는 책임도 계속 커질 것이라고 판단했습니다.

그래서 역할을 세 가지로 나눴습니다.

```text
Post              공통 게시글 데이터
 └ EventPost      모임 전용 데이터
EventApplication  사용자별 참여 신청 데이터
```

게시글 종류를 구분하는 별도의 boolean 값도 두지 않았습니다.

`EventPost`가 존재하면 모임 게시글이고, 없으면 일반 게시글로 판단했습니다. 별도의 타입 상태와 실제 연관 데이터라는 두 가지 사실을 동시에 관리하면 서로 어긋난 상태가 생길 수 있기 때문입니다.

이전에는 엔티티를 나눈다는 것을 단순히 코드가 길어지지 않게 하기 위한 작업으로 생각했습니다. 이번에는 **어떤 데이터가 함께 변경되고 어떤 규칙을 공유하는가를 기준으로 책임을 나누는 것**에 더 가깝다는 것을 경험했습니다.

---

## 애플리케이션 검증과 DB 제약의 역할을 구분했다

`EventApplication`에는 사용자와 모임의 조합에 UNIQUE 제약을 걸었습니다.

서비스 코드에서도 이미 신청한 사용자인지 확인하고 있었기 때문에 처음에는 DB 제약이 중복처럼 느껴졌습니다.

하지만 두 요청이 동시에 들어오면 다음과 같은 상황이 가능합니다.

```text
요청 A → 중복 없음 확인
요청 B → 중복 없음 확인

요청 A → INSERT
요청 B → INSERT
```

애플리케이션에서 `exists`를 확인하는 것과 실제 INSERT는 하나의 원자적 연산이 아닙니다.

그래서 역할을 나눴습니다.

```text
애플리케이션 검증
→ 사용자에게 빠르고 이해 가능한 오류 제공

DB UNIQUE 제약
→ 어떤 경쟁 상황에서도 최종 불변식 보장
```

이 결정은 이후 실제 동시성 테스트에서 그대로 필요해졌습니다.

MySQL의 REPEATABLE READ 환경에서 애플리케이션의 중복 검사가 앞선 트랜잭션의 신청 결과를 보지 못하는 상황이 발생했지만, DB의 UNIQUE 제약이 마지막 방어선으로 동작했습니다.

이 경험 이후에는 **서비스 코드에서 검사하고 있으니 DB 제약은 필요 없다는 식으로 생각하지 않게 됐습니다.**

## 저장할 상태와 계산할 상태를 구분하게 됐다

모임에는 `OPEN`, `FULL`, `EXPIRED` 같은 상태가 필요했습니다.

처음에는 상태 값을 DB 컬럼에 직접 저장하는 방법도 생각했습니다.

하지만 이 상태는 이미 존재하는 데이터에서 결정할 수 있었습니다.

```text
capacity <= applicationCount
→ FULL

deadline <= 현재 시각
→ EXPIRED

그 외
→ OPEN
```

특히 마감 상태가 문제였습니다.

DB에 `OPEN`을 저장하면 마감 시간이 지난 순간 누군가 값을 `EXPIRED`로 변경해야 합니다. 그 시점에 아무 요청도 없다면 실제 상태와 DB 값이 달라질 수 있습니다.

그래서 원본 데이터에서 결정할 수 있는 상태는 필요할 때 계산하도록 했습니다.

이 경험을 통해 **DB에 값을 더 저장한다고 항상 정합성이 좋아지는 것은 아니며, 파생 값을 저장하면 오히려 동기화해야 할 상태가 하나 늘어날 수 있다는 것**을 배웠습니다.

## 코드 구조뿐 아니라 HTTP 요청 형태까지 설계의 일부였다

모임 데이터를 입력받는 DTO는 처음에 `MeetingInfo` 객체로 중첩했습니다.

도메인만 보면 다음 구조가 더 자연스러워 보였습니다.

```text
PostRequest
 └ MeetingInfo
      ├ capacity
      └ deadline
```

하지만 실제 요청은 JSON이 아니라 `multipart/form-data`와 `@ModelAttribute` 기반이었습니다.

기존 프론트엔드는 모임 관련 값을 모두 최상위 필드로 보내고 있었고, 중첩 구조를 사용하려면 요청 계약까지 변경해야 했습니다.

처음에는 Setter 문제라고 생각했지만 Setter를 추가한 뒤에도 해결되지 않았고, 결국 문제는 Java 객체만의 구조가 아니라 **HTTP 요청 구조와 DTO 구조가 서로 맞지 않는 것**이었습니다.

DTO를 평탄화하고 모임 게시글일 때만 필요한 값들을 별도로 검증하도록 변경했습니다.

JSON이었다면 중첩 객체를 유지했을 수도 있습니다.

이 경험 이후에는 코드 내부에서 가장 깔끔한 구조만 보는 것이 아니라 **클라이언트가 실제로 어떤 형식으로 데이터를 전달하는가까지 포함해서 API를 설계해야 한다**고 생각하게 됐습니다.

## 동시성 제어도 상황에 맞게 선택해야 했다

선착순 참여에서 가장 중요한 요구사항은 최대 정원을 넘기지 않는 것이었습니다.

동시에 여러 요청이 같은 신청 인원을 읽으면 모두 신청 가능하다고 판단할 수 있습니다.

낙관적 락도 검토했지만, 선착순 신청은 충돌이 드문 상황이 아니라고 판단했습니다.

모집이 시작된 직후 동일한 `EventPost`에 요청이 몰리는 것이 자연스러운 기능이기 때문입니다.

충돌이 발생한 뒤 롤백과 재시도를 반복하기보다 처음부터 공유 자원을 잠그고 순서대로 처리하는 비관적 락을 선택했습니다.

락 대상도 신청 한 건을 의미하는 `EventApplication`이 아니라 정원과 현재 신청 인원을 공유하는 `EventPost`로 정했습니다.

하지만 실제 MySQL 환경에서 테스트하면서 `FOR UPDATE`가 정상 실행되는데도 정원이 지켜지지 않는 문제를 만났습니다.

이 문제를 추적하면서 DB의 락만 이해해서는 부족했고,

```text
MySQL row lock
Hibernate 1차 캐시
연관관계 fetch 전략
트랜잭션 격리 수준
```

까지 함께 이해해야 했습니다.

구체적인 과정은 별도의 백엔드 트러블슈팅 문서에 정리했습니다.

---

## 하나의 락으로 모든 문제를 해결하지 않게 됐다

처음에는 동시성 문제가 나오면 "어디에 락을 걸어야 할까?"부터 생각했습니다.

하지만 테스트를 확장하면서 하나의 요청에서도 서로 성격이 다른 공유 상태가 있다는 것을 알게 됐습니다.

최종적으로는 다음처럼 나눴습니다.

```text
모임 정원
→ EventPost 비관적 락

댓글 수 증가
→ 원자적 UPDATE

중복 신청
→ UNIQUE 제약
```

예를 들어 `commentCount`까지 안전하게 만들기 위해 `Post` 행 전체를 비관적으로 잠그면 일반 댓글 작성까지 모두 직렬화됩니다.

단순한 증가 연산이라면

```sql
comment_count = comment_count + 1
```

처럼 DB가 직접 원자적으로 처리하는 것이 더 적합했습니다.

반면 한 사용자가 하나의 모임에 한 번만 신청할 수 있다는 규칙은 UNIQUE 제약으로 표현하는 것이 자연스러웠습니다.

이 경험을 통해 **동시성 제어는 락이라는 기술 하나를 적용하는 문제가 아니라 어떤 불변식을 보호하려는지에 따라 다른 수단을 선택하는 문제**라고 이해하게 됐습니다.

## 테스트에 대한 생각이 가장 많이 바뀌었다

처음에는 TDD로 진행하고 싶었지만 구현부터 시작하는 경우가 많았습니다.

그래도 구현 이후 서비스 단위 테스트를 작성하며 기능을 검증했습니다.

마지막 동시성 문제를 해결하면서 테스트에 대한 기준이 크게 달라졌습니다.

이번 문제 중 일부는 Mockito 기반 단위 테스트에서는 재현할 수 없었습니다.

실제 MySQL의 row lock과 트랜잭션 격리 수준, Hibernate의 영속성 컨텍스트가 동시에 작동해야 드러나는 문제였기 때문입니다.

처음 사용하던 H2 역시 MySQL의 동시성 동작을 검증하는 환경으로는 신뢰하기 어렵다고 판단해 Testcontainers 기반 MySQL 8.4 환경으로 변경했습니다.

특히 인상 깊었던 것은 `commentCount` 문제였습니다.

처음 테스트에서는 모임 신청 인원만 확인했습니다.

나중에 댓글 수까지 assertion에 추가하자 모임 기능과 상관없이 일반 댓글에도 원래 존재하던 lost update가 드러났습니다.

여기서 한 가지를 크게 배웠습니다.

**테스트가 통과했다는 것은 내가 검증한 조건이 맞다는 의미이지, 확인하지 않은 모든 상태가 정상이라는 의미는 아니었습니다.**

현재는 다음 정도의 기준을 갖게 됐습니다.

```text
단순한 비즈니스 로직
→ 단위 테스트

DB 락·트랜잭션·ORM 동작이 정확성의 일부
→ 실제 DB를 포함한 통합 테스트
```

모든 테스트를 무겁게 만드는 것이 아니라 **무엇을 검증하려는지에 따라 필요한 계층을 테스트에 포함시키는 것**이 중요하다고 생각합니다.

## 백엔드에서 가장 크게 달라진 점

프로젝트 초반에는 문제가 생기면 코드 전체를 보면서 어디가 잘못됐는지를 막연하게 찾았습니다.

마지막에는 문제를 조금 더 나눠서 보게 됐습니다.

```text
HTTP 요청인가?
서비스 로직인가?
JPA/Hibernate인가?
트랜잭션인가?
DB인가?
```

그리고 각 계층에서 확인된 사실을 기준으로 다음 검증 방법을 정하려 했습니다.

13주 동안 Spring Boot의 기능을 더 많이 알게 된 것도 중요했지만, 개인적으로는 **서버에서 발생한 문제를 어떤 계층으로 나누고 어떻게 증거를 확인할지를 조금씩 알게 된 것**이 더 큰 변화였습니다.

앞으로도 단순히 동작하는 코드를 작성하는 것에서 끝나지 않고, 왜 이 구조를 선택했고 어떤 상황까지 안전한지를 설명할 수 있는 백엔드 개발자가 되고 싶습니다.

## 앞으로 더 해보고 싶은 것

프로젝트 기간 동안 다루지 못한 부분도 남아 있습니다.

* 게시글 목록과 상세 API의 실제 쿼리 수 측정
* Fetch Join, EntityGraph, Batch Fetch 비교 및 필요한 방식 적용
* 배포 직후 API 응답 시간이 증가한 원인을 애플리케이션·DB·네트워크 구간으로 분리해 측정

기능을 더 추가하기보다 **현재 만들어놓은 서버가 어떤 조건에서 느려지고 어떤 실패에 안전한지를 검증하는 방향**으로 이어가고 싶습니다.
